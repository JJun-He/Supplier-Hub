# 구현 계획

## 1. 진행 원칙

구현은 독립적으로 검토할 수 있는 기능 단위로 나눈다. 각 단계는 명확한 완료 조건을 가지며 관련 테스트가 통과한 상태에서 커밋한다. 파일을 만들 때마다 커밋하거나 구현을 끝낸 뒤 인위적으로 이력을 쪼개지 않는다.

가장 먼저 완성할 것은 Supplier 목록 동기화부터 통합 검색 응답까지 이어지는 한 개의 완전한 흐름이다. 선택 기능인 캐시, 서킷 브레이커, Supplier 간 동일 숙소 병합, 예약 흐름은 필수 동작과 실패 시나리오를 검증한 뒤 검토한다.

## 2. 제안하는 프로젝트 구조

```text
src/main/java/com/supplierhub
├── catalog
│   ├── application
│   ├── domain
│   └── infrastructure
├── search
│   ├── api
│   ├── application
│   └── domain
├── supplier
│   ├── common
│   ├── suppliera
│   └── supplierb
└── shared

mock-supplier
└── 별도 포트에서 실행되는 최소 Mock 애플리케이션

docs
├── architecture-decisions.md
└── implementation-plan.md
```

최상위 패키지는 기술 계층보다 기능을 먼저 구분한다. Supplier 전송 DTO는 Supplier별 infrastructure 패키지 안에 둔다. 도메인 모델이 Jackson 응답 구조나 Supplier 필드명에 의존하지 않게 한다.

Mock은 메인 애플리케이션과 실행 포트와 생명주기를 분리하되, 제품 코드 수준으로 확장하지 않는다. 최소한의 독립 실행 모듈 또는 애플리케이션이면 충분하다.

## 3. 단계별 구현 순서

### 0단계: 기반 검증과 저장소 정리

작업:

- Java 21과 현재 Spring Boot 버전으로 기본 빌드가 성공하는지 확인한다.
- 의존성 조합과 테스트 구성이 실제로 동작하는지 확인한다.
- DB와 Supplier URL을 위한 설정 구조를 만든다.
- PostgreSQL을 재현 가능하게 실행할 작은 Compose 구성을 추가한다.
- Entity를 만들기 전에 schema migration 도구를 설정한다.
- API 키는 환경 변수 또는 Git에서 제외된 로컬 설정으로 주입한다.
- 생성물과 로컬 IDE 파일이 추적되지 않는지 확인한다.

완료 조건:

- 깨끗한 checkout에서 DB를 띄우고 기본 테스트를 실행할 수 있다.
- 실제 자격 증명과 외부 원문 자료가 추적되지 않는다.
- 프레임워크 버전과 의존성이 함께 정상 해석된다.

권장 커밋:

```text
build: 로컬 DB와 migration 설정
```

### 1단계: 독립 실행 Mock Supplier

작업:

- Mock을 메인 애플리케이션과 다른 포트에서 실행한다.
- 두 Supplier의 목록 API와 재고·요금 API를 구현한다.
- Supplier별로 `normal`, `error`, `no-response` 모드를 전환할 수 있게 한다.
- `no-response`는 클라이언트 타임아웃을 확실히 넘도록 응답을 지연한다.
- 가격 형태 차이, 재고 최솟값, Supplier별 오류 표현을 검증할 최소 고정 데이터를 사용한다.
- Mock 구현 품질과 데이터 양을 필요 이상으로 확장하지 않는다.

완료 조건:

- 두 Supplier의 목록과 정상 검색이 응답한다.
- 한 Supplier의 모드를 바꿔도 다른 Supplier에는 영향을 주지 않는다.
- 무응답 모드가 실제 WebClient 타임아웃을 발생시킨다.

권장 커밋:

```text
test: Supplier Mock 시나리오 추가
```

### 2단계: 매핑 영속화

작업:

- `Supplier`, `Property`, `RoomType`을 정의한다.
- `BIGINT` PK, 고유 제약, FK, 활성 상태를 migration으로 생성한다.
- 활성 여부와 관계없이 Supplier 키로 기존 매핑을 찾는 Repository를 구현한다.
- 검색에서는 숙소와 객실 타입이 모두 활성인 매핑만 반환한다.
- Entity와 외부 API DTO를 분리한다.

완료 조건:

- 같은 Supplier 숙소 매핑을 중복 저장할 수 없다.
- 서로 다른 숙소는 같은 객실 타입 코드를 가질 수 있다.
- 비활성 매핑은 동기화에서 찾을 수 있지만 검색에서는 제외된다.

권장 커밋:

```text
feat: Supplier 카탈로그 매핑 영속화
```

### 3단계: 목록 어댑터와 카탈로그 동기화

작업:

- API 키 헤더를 포함하는 Supplier별 목록 `WebClient`를 구현한다.
- Supplier별 성공 규약을 확인한 뒤 데이터를 읽는다.
- Supplier DTO를 공통 카탈로그 snapshot으로 변환한다.
- Supplier 단위 트랜잭션으로 숙소와 객실 타입을 upsert한다.
- 재등장한 매핑은 다시 활성화한다.
- 정상적인 전체 snapshot에서 두 번 연속 누락된 매핑만 비활성화한다.
- 기존 활성 매핑을 모두 제거하는 빈 목록은 장애 가능성이 있으므로 반영하지 않는다.
- 기동 시 즉시 실행하고 설정된 주기로 반복한다.
- 일시적 오류에만 제한적 재시도를 적용한다.
- 실패 시 기존 매핑을 보존한다.

완료 조건:

- 같은 목록을 여러 번 동기화해도 내부 ID가 유지된다.
- 숙소명이 변경되어도 내부 ID는 바뀌지 않는다.
- 정상 전체 목록에서 두 번 연속 사라진 항목이 비활성화된다.
- 한 번 누락된 항목이 다시 등장하면 누락 횟수가 초기화된다.
- 비활성 항목이 다시 등장하면 이전 ID로 활성화된다.
- 한 Supplier의 실패가 다른 Supplier의 반영을 rollback하지 않는다.

권장 커밋:

```text
feat: Supplier 목록 어댑터 구현
feat: 카탈로그 동기화와 매핑 보존
test: 카탈로그 식별자 생명주기 검증
```

### 4단계: 검색 조건과 Offer 도메인

작업:

- `SearchCriteria`, 날짜 범위, `Money`, `Price`, `NightlyPrice`, 재고, `Offer`를 구현한다.
- Supplier 호출 전에 고객 입력을 검증한다.
- 서로 다른 가격 형태를 세금 포함 숙박 전체 총액으로 변환한다.
- 요청한 모든 숙박일이 정확히 한 번씩 있는지 확인한다.
- 연박 재고를 일별 재고의 최솟값으로 계산한다.
- 품절 Offer를 제외한다.
- 잘못된 Offer 하나가 정상 형제 Offer를 제거하지 않도록 결과를 분리한다.

완료 조건:

- 날짜별 세전 가격과 세금의 합이 정확한 전체 결제 금액이 된다.
- 이미 세금이 포함된 총액을 다시 계산하지 않는다.
- 날짜 누락·중복·범위 초과가 해당 Offer를 제외한다.
- `3, 1, 5`와 같은 재고는 예약 가능 객실 수 1로 계산된다.
- 요청 기간 중 하나라도 0이면 Offer가 제외된다.
- 통화가 다른 가격을 서로 비교하지 않는다.

권장 커밋:

```text
feat: Supplier 가격과 재고 정규화
```

### 5단계: Supplier 검색 어댑터

작업:

- Supplier별 재고·요금 요청과 응답 DTO를 구현한다.
- HTTP 200 본문의 실패 코드 확인을 해당 Supplier 어댑터 안에서 수행한다.
- Supplier별 오류를 공통 실패 분류로 변환한다.
- 연결, 응답, 호출 전체 제한 시간을 적용한다.
- 활성 내부 매핑이 있는 숙소와 객실 타입만 Offer로 만든다.
- Supplier 전송 DTO가 어댑터 밖으로 나가지 않게 한다.

완료 조건:

- Supplier별 경로, query parameter, API 키 헤더가 정확하다.
- HTTP 오류와 본문 오류가 같은 공통 실패 의미로 변환된다.
- 알 수 없는 매핑과 잘못된 항목은 안전하게 제외된다.
- 무응답 Mock이 무한 대기하지 않고 `TIMEOUT`으로 끝난다.

권장 커밋:

```text
feat: Supplier A 검색 어댑터 구현
feat: Supplier B 검색 어댑터 구현
```

### 6단계: 제한 병렬 통합 검색

작업:

- 활성 매핑 전체를 읽어 Supplier별로 분류한다.
- 숙소 코드를 최대 50개씩 나눈다.
- 서로 다른 Supplier를 병렬 실행한다.
- Supplier별 동시 호출을 최대 4개로 제한한다.
- 일부 묶음이 실패해도 완료된 묶음 결과를 보존한다.
- 검색 전체 5초 제한을 적용한다.
- 전체 제한을 넘긴 실행·대기 작업을 취소하고 실패로 기록한다.
- Supplier별 상태와 전체 상태를 계산한다.
- 고객 검색에서는 재시도하지 않는다.

완료 조건:

- 숙소 51개가 50개와 1개 요청으로 분리된다.
- Supplier A가 끝나기 전에 Supplier B 호출도 시작된다.
- 실제 동시 호출 수가 설정값을 넘지 않는다.
- 한 묶음 실패가 완료된 Offer를 제거하지 않는다.
- 전체 응답이 설정된 검색 시간 안에 끝난다.

권장 커밋:

```text
feat: 제한 병렬 Supplier 검색 통합
```

### 7단계: 고객 검색 API

작업:

- 버전이 포함된 검색 endpoint를 구현한다.
- 응답을 `stays[].roomTypes[].offers[]`로 그룹화한다.
- 내부 ID, 이름, 최대 수용 인원, 재고, Supplier, 조식 여부, 통화, 세금 포함 총액을 반환한다.
- Supplier 숙소·객실 코드를 노출하지 않는다.
- 전체 상태와 Supplier별 결과를 포함한다.
- 안정적인 입력 오류 응답 구조를 만든다.
- 모든 Supplier 실패를 HTTP 503으로 변환하면서 실패 본문을 유지한다.
- 필수 동작을 완성한 뒤 여유가 있으면 OpenAPI 문서를 추가한다.

완료 조건:

- 요구되는 최소 검색 정보가 모두 존재한다.
- 결과가 없을 때 배열이 `null`이 아니라 빈 배열이다.
- 정상 빈 결과, 부분 실패, 전체 실패를 구분할 수 있다.
- 잘못된 검색 조건은 Supplier 호출 전에 HTTP 400으로 끝난다.

권장 커밋:

```text
feat: 통합 숙박 검색 API 제공
```

### 8단계: 연동 견고성 검증과 지표

작업:

- 정상, HTTP 오류, 본문 오류, 무응답 Mock 모드를 실제로 실행한다.
- Supplier 호출과 전체 검색의 제한 시간을 검증한다.
- 정상 빈 결과와 조회 불가 결과를 별도 테스트한다.
- Offer 단위와 호출 묶음 단위 부분 실패를 검증한다.
- 고객 검색이 재시도되지 않는지 확인한다.
- Supplier별 호출 결과, 지연, 타임아웃, 제외 Offer, 목록 동기화 지표를 추가한다.
- Metric label에 숙소 코드나 예외 메시지가 들어가지 않게 한다.

완료 조건:

- 정상·장애·무응답 시나리오를 문서의 명령으로 재현할 수 있다.
- 최종 값뿐 아니라 호출이 실제 병렬로 시작되는지도 테스트한다.
- HTTP 200인 부분 실패도 Supplier 지표에서 실패로 확인된다.
- 깨끗한 checkout에서 전체 자동 검증이 통과한다.

권장 커밋:

```text
test: 타임아웃과 부분 실패 동작 검증
feat: Supplier 연동 지표 추가
```

완료 조건:

## 4. 테스트 전략

### 4.1 단위 테스트

규칙과 경계값을 중심으로 테스트한다.

- 체크아웃일을 제외한 날짜 범위 생성
- 날짜와 인원 입력 검증
- 세금 포함 전체 금액 계산
- 요청 기간의 날짜 완전성
- 연박 재고 최솟값
- 품절 Offer 제외
- Supplier 오류의 공통 분류
- 전체 검색 상태 계산
- 숙소 코드 0, 1, 50, 51개와 더 큰 수의 분할

Getter, 생성자, 프레임워크 자체 동작만 반복해서 확인하는 테스트는 작성하지 않는다.

### 4.2 Repository 테스트

선택한 관계형 DB의 실제 동작을 기준으로 다음을 확인한다.

- 고유 제약
- 비활성 매핑 검색 제외
- 비활성 매핑 재활성화
- 재동기화 후 내부 ID 유지
- 객실 타입 코드의 숙소별 유일성

PostgreSQL 전용 타입이나 migration을 사용한다면 인메모리 DB만으로 검증하지 않고 PostgreSQL 기반 통합 테스트를 우선한다.

### 4.3 HTTP 어댑터 테스트

제어 가능한 HTTP 서버를 사용해 다음을 확인한다.

- 요청 경로와 query parameter
- API 키 헤더
- Supplier별 성공·실패 판정
- JSON 파싱 실패와 의미상 잘못된 응답
- 응답 타임아웃
- 실시간 검색 재시도 없음

### 4.4 End-to-end 테스트

| 시나리오 | 기대 결과 |
| --- | --- |
| 두 Supplier 모두 성공 | HTTP 200, `COMPLETE` |
| 한 Supplier 실패 | HTTP 200, `PARTIAL`, 정상 Offer 유지 |
| 한 Offer만 잘못됨 | HTTP 200, `PARTIAL`, 정상 형제 Offer 유지 |
| 모든 Supplier 실패 | HTTP 503, `FAILED` |
| 모든 Supplier 성공, 상품 전부 품절 | HTTP 200, `COMPLETE`, 빈 `stays` |
| 한 Supplier 정상 빈 결과, 다른 Supplier 실패 | HTTP 200, `PARTIAL`, 빈 `stays` |
| 한 Supplier 무응답 | 설정된 시간 안에 응답 완료 |
| 숙소 코드 50개 초과 | 최대 50개씩 정확히 분할 |

## 5. 커밋 계획

구현 중 발견한 실제 작업 경계에 따라 커밋 수는 조정할 수 있다. 기본 흐름은 다음과 같다.

```text
docs: 설계 결정과 구현 계획 정리
build: 로컬 DB와 migration 설정
test: Supplier Mock 시나리오 추가
feat: Supplier 카탈로그 매핑 영속화
feat: Supplier 목록 어댑터 구현
feat: 카탈로그 동기화와 매핑 보존
test: 카탈로그 식별자 생명주기 검증
feat: Supplier 가격과 재고 정규화
feat: Supplier A 검색 어댑터 구현
feat: Supplier B 검색 어댑터 구현
feat: 제한 병렬 Supplier 검색 통합
feat: 통합 숙박 검색 API 제공
test: 타임아웃과 부분 실패 동작 검증
feat: Supplier 연동 지표 추가
docs: 실행 방법과 설계 근거 정리
```

커밋 원칙:

- 동작하거나 독립적으로 검토할 수 있는 단위로 커밋한다.
- 기능 커밋에 무관한 리팩터링을 섞지 않는다.
- 각 커밋 전에 관련 테스트를 실행한다.
- 판단이 바뀐 과정은 숨기지 않고 `JOURNAL.md`에 이유를 남긴다.
- 구현을 모두 끝낸 뒤 인위적으로 과거 이력을 만들지 않는다.
- 외부 조직명이나 원문을 떠올리게 하는 표현을 커밋 메시지에 사용하지 않는다.

## 7. 구현을 막지 않는 미확정 설정

다음 값은 Mock 기반 첫 측정 후 조정할 수 있도록 설정으로 둔다.

- 카탈로그 동기화 실행 간격
- 카탈로그 재시도 횟수와 backoff
- 카탈로그 전용 타임아웃
- Supplier별 동시 호출 수 override
- 로그 sampling과 metric 이름
- 필수 기능 완료 후 OpenAPI 자동 문서 포함 여부

이 값들은 확정한 도메인 모델과 API 응답 의미를 바꾸지 않는다.
